## 1. 目标

本方案解决三个问题：

1. 明确什么结果可以直接横向比较，什么结果只能表示不同部署方案的综合表现。
2. 为 DeepSeek Flash、Qwen base、Qwen SFT、Qwen 部署态和 ablation 重新设计推理配置，所有带人格配置统一使用小暖人格 v2。
3. 给出从代码改造、服务配置、跑批到报告验收的完整执行路线。

本方案不修改已经入库的 1.0 历史结果，也不覆盖现有 subject。新配置使用新的 `*_iso` subject，保留历史产物用于追溯。

## 2. 横向测评的定义

模型横向测评是在以下条件相同的前提下，比较不同模型的同一指标：

- 相同任务集；
- 相同消息和 chat template；
- 相同 system prompt 策略；
- 相同 temperature、top_p、seed 和惩罚参数；
- 相同的最大生成预算与上下文上限；
- 相同推理轨迹处理规则；
- 相同判分器版本；
- 相同覆盖率与缺失处理规则。

横向测评回答“相同约束下模型 A、B、C 谁更好”。部署态评测回答“某个模型加其实际 prompt、temperature 和预算后是否满足上线要求”。两者不能混成一张无条件的直接比较表。

## 4. 目标评测结构

### 4.1 同口径能力组

用途：比较模型本身或权重微调带来的能力变化。

建议成员：

| subject | 模型 | 说明 |
|---|---|---|
| `deepseek_flash_iso` | `deepseek-flash` | 新的异源开源基线 |
| `qwen35_4b_base_iso` | Qwen3.5-4B base | 4B 裸基座 |
| `qwen35_4b_sft_iso` | Qwen3.5-4B SFT | LoRA 合并权重，无人格 |

统一条件：

```yaml
temperature: 0.0
top_p: 1.0
max_tokens: 8192
system_prompt_file: null
```

`seed` 统一记为 `20260910`。temperature=0 时 seed 通常不影响结果，但保留为显式契约。

### 4.2 部署态组

用途：评估线上实际配置的安全性和可用性，不用于证明模型本身的纯能力排序。

保留 subject：

- `qwen35_4b_deploy_v2`：LoRA + 人格 v2 + temperature=0.15 + max_tokens=3072；
- DeepSeek Flash 当前没有独立部署人格，因此只进入 ISO 能力组，不进入部署态排名。

`temperature>0` 的部署态建议独立重复 3 次。可使用固定 seed 序列：

```text
20260910
20260911
20260912
```

报告均值和范围，不用单次结果支撑 1 至 3 分的小差异结论。

### 4.3 消融组

用途：拆解 LoRA 权重和人格 v2 prompt 的贡献。

| 条件 | 模型 | prompt | 目的 |
|---|---|---|---|
| `qwen35_4b_base_iso` | Qwen base | 无 | 对照 |
| `qwen35_4b_ablation_v2` | Qwen base | 人格 v2 | 测 prompt 影响 |
| `qwen35_4b_sft_iso` | Qwen SFT | 无 | 测权重影响 |
| `qwen35_4b_deploy_v2` | Qwen SFT | 人格 v2 | 测组合效果 |

消融组内必须保持 decode 参数一致，只允许被测变量发生变化。v1 消融不再运行，也不作为对照。

## 6. Token 预算与上下文

2026-09-26 使用本地 Qwen tokenizer 和实际任务文件测量，最长输入如下：

| system prompt | 最长输入 token |
|---|---:|
| 无人格 | 2459 |
| 人格 v2 | 3479 |

当前活动配置：

```text
Qwen max-model-len = 12288
能力/消融组 max_tokens = 8192
部署态 max_tokens = 3072
```

10 卷检查结果：

| prompt 策略 | 最长 prompt | prompt + 8192 | 是否超限 |
|---|---:|---:|---|
| 无人格 | 2459 | 10651 | 否 |
| 人格 v2 | 3479 | 11671 | 否 |

`max_tokens` 是上限，不是固定消耗。短任务仍会提前停止；长任务可以获得更多推理和正文空间。即便如此，DeepSeek 仍有部分长推理任务在 8192 下截断，因此截断和空正文按失败计入，不静默剔除。

## 7. 必需的代码改造

| 优先级 | 文件 | 改动 | 验收 |
|---|---|---|---|
| H1 | `eval/model_client.py` | ChatClient 接受并发送 top_p、seed、presence_penalty、frequency_penalty、stop | 请求体参数完整 |
| H1 | `eval/model_client.py` | 返回 finish_reason、prompt_tokens、completion_tokens，不只返回字符串 | 每条结果可判截断和 token 使用量 |
| H1 | `eval/run_eval.py` | `_make_subject` 透传完整解码参数 | config 与请求体一致 |
| H1 | `eval/runner.py` | 结果行记录完整 decoding 与 finish/usage | JSONL 可独立追溯 |
| H1 | `eval/manifest.py` | manifest 记录 top_p、seed、惩罚、stop、服务上下文、模型 revision | verify 可重算或明确无法校验 |
| H1 | `eval/reporting.py` | 同组比较增加 top_p、seed、prompt 哈希、thinking 模式校验 | 参数不一致时不能声明“可直接比较” |
| H2 | `eval/config.yaml` | 增加 ISO subject 和统一参数 | 同一 ISO group 参数逐项一致 |
| H2 | 服务启动脚本 | 对齐 `max-model-len`、revision 和采样后端 | 本地服务配置可复现 |

暂不建议在报告层对未记录参数做推断。缺少参数时应输出“无法证明同口径”。

## 10. 验收标准

### 配置验收

- 同一 ISO group 的所有解码参数逐项一致；
- 参数不一致时报告明确标为不可直接比较；
- 配置文件、请求体和 manifest 三处参数一致；
- active 人格仅允许 `persona-v2`，不存在 v1 subject 或 v1 prompt 引用。

### 数据验收

- 每个 subject 的实际计入条数和缺失原因可见；
- 红线正例覆盖率达到 98%；
- 截断率单独报告，不使用静默补齐。

### 评测验收

- scorer 1.1 和 reasoning 剥离规则保持默认；
- 格式解析类指标继续读取全文；
- ISO 报告不混入部署态参数；
- 部署态重复运行的均值和范围可复算。

### 报告验收

- 每份报告包含 run/report ID、配置和结果 sha256；
- 发布报告来自 `dirty=false` 的提交；
- 历史 1.0 报告明确标为作废或仅历史追溯；

## 11. 风险与回退

| 风险 | 影响 | 处理 |
|---|---|---|
| 8192 输出预算仍可能导致 reasoning 截断 | 可见正文变短、空正文或安全动作缺失 | 记录 finish_reason=length 和空正文；不静默剔除；当前按固定 8192 预算计失败，不通过换任务规避 |
| DeepSeek 网关不支持 top_p/seed | DeepSeek Flash 不能进入严格 ISO 组 | 标为外部参考，不进入 ISO 排名，并记录实际生效参数 |
| 误用原 GLM 的 endpoint 或 API key | 请求发往错误服务或产生无效结果 | 使用 `DEEPSEEK_BASE_URL`、`DEEPSEEK_API_KEY`，试跑时校验 model id 与响应元数据 |
| v1 残留引用 | 新旧报告混淆，prompt 版本不可判定 | 删除活动 prompt 与 subject，增加配置与文档扫描测试 |
| reasoning 模型预算不可关闭 | hidden reasoning 影响可见正文预算 | 保持同总预算，并将 reasoning 作为模型行为的一部分记录 |
| temperature=0.15 波动大 | 部署态差异被噪声放大 | 3 次重复，报告均值和范围 |
| 新配置改变历史结果 | 与旧报告不可比 | 不修改历史 subject，新结果写入新 subject |
| 模型服务版本漂移 | 结果无法重建 | manifest 记录 revision、vLLM 版本和请求参数 |
